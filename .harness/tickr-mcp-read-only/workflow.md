## Revision 3 changes

Revision 2 (SHA-256 `3a457e30…da2ad`) cited spec revision 1. Revision 3 rebuilds the workflow on [spec revision 2](context-spec.md).

- **Gate removed.** The staging spike is replaced by a pinned dependency step and a local proof with MCP Inspector against a Neon branch. The staging proof with Codex moves to QA, before rollout.
- **Authentication settled.** Opaque access tokens use a Tickr-supplied hash, so `/api/mcp` verifies tokens with one indexed lookup. The audience check is replaced by the `time_entries:read` scope plus explicit REST rejection of a token prefix.
- **Phase A is done** (steps 2, 6, 10a at `0c8073b`) and is carried over unchanged.

## Affected entry points and dependencies

- **New dependencies, pinned exactly.** `@better-auth/oauth-provider@1.6.18` and `@modelcontextprotocol/sdk@1.32.2`. The SDK ships `server/webStandardStreamableHttp.js` and exports `./server` and `./*`. `@better-auth/cli` is published only up to 1.4.21, so the Drizzle tables are written by hand from the plugin's `schema` object.
- **New HTTP entry points.**
  - `src/routes/api/mcp.ts` is the MCP endpoint.
  - `src/routes/[.]well-known/oauth-protected-resource/api/mcp.ts` and `src/routes/[.]well-known/oauth-authorization-server/api/auth.ts` serve metadata. They follow the bracket-escape and `server.handlers` pattern of `src/routes/api/openapi[.]json.ts`.
  - The plugin's `/oauth2/*` endpoints are served by the existing `src/routes/api/auth/$.ts` → `auth.handler`.
  - `src/routes/oauth/consent.tsx` is the consent page.
- **Existing code modified.**
  - `auth` in [auth.ts](../../src/lib/auth.ts): plugin, Drizzle schema map, `hooks.before` gating, and rate-limit rules.
  - `authClient` in [auth-client.ts](../../src/lib/auth-client.ts): `oauthProviderClient()`.
  - `src/db/schema.ts`: four tables.
  - The `/auth/` route in [index.tsx](../../src/routes/auth/index.tsx): the sign-in handler and loader resume OAuth.
  - `ProfileScreen` in [ProfileScreen.tsx](../../src/components/time-tracker/screens/ProfileScreen/ProfileScreen.tsx): Connected apps.
  - The REST bearer path in [external-api-auth.server.ts](../../src/lib/server/integrations/external-api-auth.server.ts): an explicit prefix rejection.
- **Reused unchanged.** `listMyTimeEntries`, `isMcpEnabled`, `isMcpPilotUser` (Phase A), `listPersonalTimeEntries`, and `personalTimeEntriesQuerySchema`.
- **Risk areas.**
  - The auth config change touches every sign-in (C19).
  - Server code must read the Neon branch, never production (C0).
  - The migration must not disturb production-only objects (C12).
  - The `/auth` resume must not become an open redirect.
  - Unauthenticated client registration lets anyone create client rows ([Q2](context-spec.md#decisions-and-dependencies)), which rate limits bound.

## Compatibility, rollout, and recovery

- **Compatibility.** REST routes, JWT shapes, and `EXTERNAL_API_JWT_SECRET` are unchanged, except that `tmcp_`-prefixed bearers now get an immediate 401, which no existing credential uses. The plugin adds endpoints only under `/api/auth/oauth2/*` and `/.well-known/*`, all returning 404 while the flag is off.
- **Production database.** Execute never runs `db:*` with `.env` and never writes to production. Applying `0029` to production is a separate, user-confirmed step after QA, with a Neon rollback point first. See the production-database rule in [spec](context-spec.md#req-4--operate-and-verify-the-pilot).
- **Rollout.**
  1. Merge with the flag off (C2).
  2. Apply `0029` to production after confirmation.
  3. Enable for synthetic pilot IDs on staging and run C13S–C17S.
  4. Add real pilot IDs.
- **Recovery.** `MCP_ENABLED=false` stops discovery, authorization, and calls on restart. Removing an ID from the pilot list blocks that user's existing tokens on the next call. The four tables are additive. Rolling back code leaves them inert, and a later reviewed migration can drop them.
- **Ingress.** DigitalOcean must pass `Authorization` and the `/.well-known/*` paths to the app. C13S verifies this.

## Assumptions (reversible)

- **Token lifetimes (impact 2).** The access token lasts 15 minutes. The refresh token uses the plugin default of 30 days.
- **Rate limits (impact 2).** Register 5 per 10 min, token 20 per min, authorize 20 per min, and MCP calls 60 per min per client and user. They are tunable in the runbook.
- **Stateless transport (impact 2).** No `Mcp-Session-Id`, and GET returns 405. This is sufficient for one request–response tool.
- **Sign-up during authorization (impact 2).** A new user who signs up must verify their email and then restart from the client. Resuming after verification is out of scope.
